# iSkool Changelog

## [Unreleased]
### Added
- Learner Quiz Pages (Desktop): New shared include `includes/learner_theme_head.php` so the pages that open inside the learner dashboard's `#mainFrame` iframe can follow the Light / Dark choice from Settings > Appearance. Those pages are separate documents, so the `<html data-learner-theme>` attribute the dashboard sets never reached them. The include prints a small script that runs before first paint and sets `data-learner-theme` on the page's own `<html>` from the saved choice: the `iskoolLearnerDesktopTheme` localStorage key that `desktop_settings.js` writes (or a key the parent page defines through `ISKOOL_LEARNER_THEME_KEY`), falling back to the parent page's attribute when nothing is saved. It follows live changes through the `storage` event, so switching theme in the dashboard updates an open quiz without a reload, and then loads the page's light stylesheet. The stylesheet name is checked with `basename()`, the pattern `^[a-z0-9_]+\.css$` and `is_file()` before use, nothing from the request is read, and the link carries a `?v=` file-modified-time suffix (`includes/learner_theme_head.php`).
- Quiz Page (Desktop): New light stylesheet `assets/css/learner/take_quiz_light.css`. The page already runs on CSS variables, so it re-points them to the learner light palette (`#faf9f5` page, `#f4f3ee` top bar and sidebar, `#dfded8` lines, `#187a72` accent) and then fixes the colours that were hard-coded: answer options and inputs (white on the cream page), the question palette and legend, the timer warn and danger states, Previous / Next / Submit (the dark `#252624` primary button the rest of learner light mode uses), the **Submit Quiz?**, **Exit Quiz?** and **Time's Up!** modals with their backdrop and shadow, the one-minute toast, and the **Quiz Unavailable** and **Time's Up** pages `take_quiz.php` prints instead of the quiz. A few greys, the orange and the red are one shade darker than on Home so small labels on the top bar and sidebar stay at 4.5:1 contrast or better. The image lightbox stays dark on purpose, because a photo viewer reads best on a dim backdrop (`take_quiz_light.css`).
- Quiz Result Page (Desktop): New light stylesheet `assets/css/learner/submit_quiz_light.css` for the card shown after a quiz is handed in, in all three states: the score (**Quiz Complete**), **Marks Pending** and **Quiz Closed**. It sets the learner light palette on the page's variables, swaps the heavy dark card shadow for a soft one, and recolours the progress-ring track, the top bar on the closed card, the pending and closed icons, and the **Back to Gradebook** button (`submit_quiz_light.css`).
- Login Page (Desktop): Light mode for the login, register and forgot-password page. The new `assets/css/index_light.css` re-colours the three forms (inputs, labels, the Log in / Continue / Register / Back buttons, the register step bar, the four role cards, and the error and password messages that carry inline colours), the **Check your inbox** and **You're registered!** screens and the Processing overlay, on the same palette the light dashboards use (`#faf9f5` page, `#ffffff` form card, `#282924` text, `#252624` primary button with `#faf9f5` text, `#dfded8` lines, `#b0413b` errors, `#15803d` success). It covers both layouts: two panels at 900px and up, and the single column from 769px to 899px. The four role icons are a shade darker so they read on paper: Learner `176, 112, 0`, Teacher `29, 111, 184`, Parent `190, 55, 105` and School admin `110, 78, 205`. Every rule sits inside `@media (min-width: 769px)` and needs `<html data-login-theme="light">`, so dark mode and phones (768px and below) render exactly as before (`index_light.css`).
- Login Page (Desktop): New include `includes/login_theme_head.php`. The login page is shown before anyone has signed in, so it cannot read a per-account theme. Both dashboards now save the theme they last showed on this browser in `localStorage` under `iskoolDesktopThemeLastUsed` (`light` or `dark`), and this include reads it and sets `<html data-login-theme="light">` before first paint, so there is no dark flash. It follows changes made in another tab through the `storage` event and links `splash_light.css` and `index_light.css` with a `?v=` file-modified-time suffix. If the visitor is already signed in as a parent or school admin the page stays dark, because those dashboards have no light mode and the splash would otherwise change colour between the login page and the dashboard. The saved value is per browser, not per account, so on a shared computer the login page shows the theme of whoever used it last (`includes/login_theme_head.php`).
- Splash Screen (Desktop): New light splash `assets/css/splash_light.css`, shared by the login page (`#animation-wrapper`) and both dashboards' `#dash-splash` handoff, so the splash is the same colour from the login page into the dashboard: a `#faf9f5` background and a `#282924` iSkool wordmark. It applies from 769px up and needs the `light` attribute on `<html>` (`data-login-theme`, `data-learner-theme` or `data-teacher-theme`), so the dark splash and the phone splash are unchanged (`splash_light.css`).
- Login Page Animation (Desktop): The animation in the login page's left panel (`animations/features/quiz-intro.html`) is a separate document inside an iframe, so it now has its own small script that follows the parent page's `data-login-theme`, then the saved `iskoolDesktopThemeLastUsed` value, and keeps following it live. It also has a light colour block that flips the animation's colour tokens and re-colours what was written by hand for the dark paper: text, hairlines and borders, the ink-filled buttons, the answer rings, the switch, the bars, and the amber **Your call** states, which are darkened to stay readable on a light card. The dark look is unchanged. The panel is hidden below 900px, so phones and narrow windows never show it (`quiz-intro.html`).
- Parent Link (Learner, Desktop & Mobile): A learner now links a parent with a one-use **invite link** instead of picking from a list. In My Class, **Create invite link** makes a link that works once and expires after 48 hours, with a **Copy link** button. The learner sends it to their parent in whatever way they like. Nothing is sent by iSkool. A learner can have several parents, and the panel (desktop) and bottom sheet (phones) list the linked parents with a **Remove** button. New `api/learner/create_parent_invite.php`, `get_parent_links.php` and `remove_parent_link.php`, `assets/js/learner/parent_invite.js`, `assets/css/learner/parent_invite.css` and a rewritten `assets/js/learner/mobile_class.js`.
- Parent Link (Parent): New `parent_link.php`, the page the invite link opens. A signed-in parent sees the learner's name and class and confirms. A parent who is not signed in is sent to log in or register and returns to the same page afterwards (`pending_parent_invite` cookie, read by `dashboard.php`). New `api/parent/redeem_parent_invite.php` does the linking: the code is stored only as a SHA-256 hash, can be used once, expires after 48 hours, wrong codes are rate limited, and the invite is claimed atomically inside a transaction. A link opened from another website (WhatsApp Web, webmail) is bounced once to the same page from our own origin first, because the session cookie is `SameSite=Strict` and would otherwise not be sent, and starting a new session would replace the parent's real one.
- Database: **needs a manual migration on every school database before this deploys.** `migrations/2026_10_18_parent_invite_linking.sql` drops the `uniq_learner_class` key on `parent_links` (it allowed only one parent per learner per class), makes `parent_links.class_id` optional, and creates `parent_invites`. `superadmin/iskool_new_school_template.sql` has the same changes for new schools. Before running the migration on a school, run `SHOW CREATE TABLE parent_links;`. A school made from the old template has neither `uniq_learner_class` nor `unique_link`, so the `DROP INDEX` would fail and reject the whole statement. On such a school, skip the `DROP INDEX` and instead run `ALTER TABLE parent_links MODIFY class_id int(11) NULL, ADD UNIQUE KEY unique_link (parent_email, learner_email);` (remove any repeated parent and learner pairs first), then create `parent_invites`.
- Parent Link (Learner): Limits on invite links. A learner can have at most 5 unused, unexpired links open at once and can create at most 10 an hour. When a new link is created, that learner's expired links and used links older than 30 days are deleted. The shared rules (code format, hash, 48-hour expiry, display name) live in `auth/parent_invite_functions.php` (`create_parent_invite.php`, `parent_invite_functions.php`).
- Tests: `tests/ParentInviteFunctionsTest.php` for the invite helpers in `auth/parent_invite_functions.php`, and new checks in `tests/SentinelSecurityTest.php` for the invite endpoints.
- Parent App (Desktop & Mobile): A new parent app with a **Home** and a **Progress report** screen, built to look like the learner app. A parent sees the learners linked to them (`parent_links`), switches between children with the chips at the top, and everything is read-only. **Home** shows a one-line summary of the term (worded from the change since last term, never "good" or "bad"), the term average, a mark and a bar for each subject, what is coming up (assignment due dates, quizzes not yet taken, class events) and the latest announcements. **Report** shows one term at a time (buttons for Terms 1 to 4): average, highest and lowest subject, and for each subject the mark, CAPS level (1 to 7), the change since the term before and how much of the term's marks have been marked so far. Tapping a subject lists the marked work behind its mark. Light is the default and the account menu switches to dark; the choice is saved in `localStorage` under `parentApp.theme`.
- Parent App (Mobile): The phone header has the same structure as the learner's: a menu button on the left that opens a slide-in menu (with Escape, tap-outside and keyboard focus trapping), the school logo in the middle (or the school's two initials when no logo is uploaded) and a round profile button on the right with a menu holding the parent's name and email, the light / dark switch and **Sign out**. The five tabs sit in a bottom bar. Checked from 320px wide with no sideways scrolling. On desktop the same five links sit in a sidebar.
- Parent App (Data): New `api/parent/get_children.php`, `get_home.php` and `get_report.php` (GET, parent only) and the helpers in `auth/parent_app_functions.php`. A child is identified by `users.id`, learner email addresses are never sent to the browser, and every read first checks the child is linked to the signed-in parent (`parent_find_child()`), so someone else's child gives the same `404` as a child that does not exist. A mark is only shown once the teacher has published it (`quizzes.publish_marks = 1`) and every open-ended answer in that attempt has been graded. The term mark uses the same rules as the learner's progress report (`calcTermMark` in `api/learner/get_progress_report.php`: summative work only, weighted, weights scaled down above 100 and shared equally when none is set), so a parent and the learner see the same number. Announcements shown are school-wide ones with `target_role = 'all'` and class announcements a teacher sent to parents (`send_to = 'parents'`) for the learner's class this year.
- Parent App (Files): `parent_dashboard.php` is rewritten as a small page shell, with `assets/css/parent/parent_app.css` and `assets/js/parent/parent_app.js`. The script puts everything from the server on the page as text, never as markup. Both files load with a `?v=` number in `parent_dashboard.php` (see the cache-busting entries under Changed); raise it whenever they change, because the service worker caches `/assets/` by full URL (`parent_dashboard.php`).
- Parent App (Database): No new tables or columns, but the parent app needs the same manual migration as the parent invite links (`migrations/2026_10_18_parent_invite_linking.sql`), because it reads `parent_links` rows that have no class. Run it on the dev database and on every school database before this deploys.
- Parent App (Not included yet): A parent only sees events set for their child's class, not whole-school ones, because `academic_events.class_id` is required. School-wide announcements show only when they are sent to everyone (`target_role = 'all'`), as the school admin announcement API cannot target parents on its own. The unread markers in News are kept in the browser only, and the notification a teacher's announcement creates still links to the learner dashboard instead of opening News.
- Tests: `tests/ParentAppFunctionsTest.php` for the level bands, term mark weighting, average, names and initials, dates, upcoming order and the summary wording, and new checks in `tests/SentinelSecurityTest.php` that the parent endpoints are parent only, check the child before reading anything, only use published marks and send no learner emails, and that the page script never uses `innerHTML`.
- Parent App (Syllabus, Desktop & Mobile): The **Syllabus** tab now shows what the learner's teachers have posted for each subject, read-only, for the child selected at the top. Buttons for Terms 1 to 4 appear only for terms that have a syllabus, and the current term opens first. Each subject is a row with the teacher's name and the number of topics. Tapping it opens the teacher's note (shown as the teacher wrote it, line breaks kept), the numbered topics, and **How it is assessed**: a coloured bar and a list of assessment types with their weight in percent. A subject with nothing filled in yet says so, and a child with no syllabus at all gets a short "No syllabus posted yet" message. Several subjects can be open at once. It is the same information the learner sees in their own Syllabus, from the same table (`subject_briefs`), for the classes the child is in this year.
- Parent App (Syllabus, Data): New `api/parent/get_syllabus.php` (GET, parent only, `?child=<users.id>`). It checks the child is linked to the signed-in parent (`parent_find_child()`) before reading anything, so someone else's child gives the same `404` as a child that does not exist, and it never sends learner email addresses. It returns the child's name and class, the current term, the terms that have a syllabus and one entry per subject. New helpers in `auth/parent_app_functions.php`: `parent_fetch_syllabus()` reads `subject_briefs` for the classes the learner is in this year (teacher found with a `LEFT JOIN` on `users`, so a syllabus from a teacher whose account was removed still shows, under "Teacher"), and `parent_parse_topics()` and `parent_parse_assessments()` clean the stored JSON: topics must be a list of text or numbers, an assessment needs a name and a weight above 0, and malformed or hand-edited values are dropped instead of breaking the page. The page shows all of it as text, never as markup, so a topic that contains `<script>` is shown literally.
- Parent App (Syllabus, Database): No new tables or columns, but Syllabus reads `subject_briefs` with the columns the teacher and learner syllabus pages already use (`class_id`, `academic_year_id`, `term_number`, `subject_name`, `created_by`, `topics`, `assessments`, `notes`, `updated_at`). **Known problem, not fixed here:** `superadmin/iskool_new_school_template.sql` still creates `subject_briefs` with an older shape (`teacher_email` and `content` instead of those columns), so on a school made from the template the teacher, learner and parent syllabus pages all fail until the table matches the live one. The live definition, including the unique key that `api/teacher/save_sbo.php` relies on for `ON DUPLICATE KEY UPDATE`, is not in the repo. To fix the template, run `SHOW CREATE TABLE subject_briefs;` on a school where Syllabus works and use that (`auth/parent_app_functions.php`, `superadmin/iskool_new_school_template.sql`).
- Tests: `tests/ParentAppFunctionsTest.php` checks both parsers (empty, malformed, nested, zero and negative weights, markup kept as plain text), and `tests/SentinelSecurityTest.php` now runs its parent-only and child-check test over `get_syllabus.php` as well.
- Tests: two new checks in `tests/SentinelSecurityTest.php` for the parent app fixes below: the page only says "No children linked yet" after the children list has loaded, and a school with no current year gets its own message. Home, Report and Syllabus must answer with `code: "no_year"` only after the child has been checked, and the page must really move its children status to loading, ready and failed (`tests/SentinelSecurityTest.php`).
- Parent App (News, Desktop & Mobile): The **News** tab is one feed of announcements, newest first, for all of a parent's children together. Each item says whether it is from the **School** or a **Teacher**. A teacher item names the teacher and the child it is for (**Mrs Venter · for Thandi**), and when a parent has two children in the same class the notice shows once, for both. A school-wide announcement shows once, not once per child. Buttons filter by **All / School / Teacher**. Tapping an item opens the full message (line breaks kept) with when it was posted and when it was edited. Unread items have a dot and a bolder title, opening one marks it read, and **Mark all as read** clears the rest. What has been read is kept in this browser under `parentApp.read.<parent email>`, the same way the learner's announcements do it, and on a first visit anything older than 7 days counts as read. The feed shows the latest 60 and says so when there are more. The child switcher is hidden on this tab, because it covers every child. Home's **Latest news** now has a **See all** link to it.
- Parent App (News, Data): New `api/parent/get_news.php` (GET, parent only). It takes no child id: everything is found through `parent_links` for the signed-in parent, so a parent can only get notices for the classes their own children are in this year, and learner emails are never sent. A parent with no linked child gets an empty feed, not even the school's announcements. Same rules as the Home screen: school-wide means no class and `target_role = 'all'`, and a class announcement needs `send_to = 'parents'`. New helpers in `auth/parent_app_functions.php`: `parent_fetch_feed()` (the two queries), `parent_build_feed()` (merges, removes repeats, sorts, caps at the limit and says if older ones were left out), `parent_feed_item()` and `parent_join_names()` ("Thandi, Sipho and Lwazi"). It reads `announcements.edited_at` for the **Edited** date, a column `api/learner/get_announcements.php` already uses, and a `0000-00-00` value counts as never edited. When the school has no current academic year it answers with `code: "no_year"` instead of a plain error.
- Parent App (News, Database): No new tables or columns. Read and unread is kept in the browser (`localStorage`, under `parentApp.read.<parent email>`), not in the database, so it does not follow a parent from one device to another. **Known problem, not fixed here:** News reads `announcements.edited_at`, which the live table has (the learner's `get_announcements.php` reads it too) but `superadmin/iskool_new_school_template.sql` does not create. On a school made from the template, News would fail, as the learner announcements already do. To fix the template, add `edited_at` as it is in the live table (run `SHOW CREATE TABLE announcements;` on a working school) (`auth/parent_app_functions.php`, `superadmin/iskool_new_school_template.sql`).
- Tests: `tests/ParentAppFunctionsTest.php` checks the feed (newest first, school and teacher mixed, one item for two children in a class, repeats removed, the 60 cap and the "more" flag, missing titles and teachers, bad dates, markup kept as plain text) and `parent_join_names()`. `tests/SentinelSecurityTest.php` checks `get_news.php` is parent only, reads no child id from the request, goes through `parent_links` and `send_to = 'parents'`, and sends no email addresses.
- Parent App (Events, Desktop & Mobile): The **Events** tab lists what is coming up for all of a parent's children together, earliest first, for the next 120 days. It pulls **assignment due dates**, **quizzes not yet taken** and the **class events** teachers add (tests, exams, holidays, school events) from data that already exists. Items sit under **Today**, **Tomorrow**, **This week**, **Next week** and then each month. Each one shows what it is (**Assignment due**, **Quiz**, **Test**, **Holiday**...), the subject and time when there is one, and the child it is for (`for Thandi`). The same thing for two children, such as a class event or an assignment neither has handed in, shows once with both names. An assignment one child has handed in and another has not shows twice, and a handed-in one is greyed and says **Assignment handed in**. Buttons filter by **All / Work** (assignments, quizzes, tests, exams) **/ School** (holidays and school events). The latest 80 are shown, with a line saying so when there are more. The child switcher is hidden on this tab. Home's **Coming up** now has a **See all** link to it. This finishes the five tabs.
- Parent App (Events, Data): New `api/parent/get_events.php` (GET, parent only). It takes no child id or date: everything is found through `parent_links` for the signed-in parent, so a parent only gets items for their own children's classes this year, and learner emails are never sent. A parent with no linked child gets an empty list. New helpers in `auth/parent_app_functions.php`: `parent_linked_learners()` (the parent's learners, with the email kept on the server), `parent_fetch_events()`, `parent_build_events()` (merges the same item across children, sorts, caps and says if later ones were left out), `parent_event_item()`, `parent_event_group()` (the headings, with weeks running Monday to Sunday) and `parent_event_section()`. A date with no time (a class event) sorts before timed items on the same day, and midnight counts as "no time set".
- Parent App (Events, Not included yet): Work that was due before today and has not been handed in is not listed, because the list starts at the beginning of today, and that is probably what a parent most wants to know. An **Overdue** group above **Today** would add it (`parent_fetch_events()` in `auth/parent_app_functions.php`).
